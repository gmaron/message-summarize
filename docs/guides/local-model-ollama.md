# Choosing a local model (Ollama)

A small model, 3 to 8 billion parameters, can summarize on your own machine. Which one suits you depends on your RAM and how well it does the job, so the program has a table of candidates and a way to measure them (RF-45). Back to the [README](../../README.md).

**You choose the model; the program does not pick one for you.** It lists the candidates that fit in your RAM, shows what was measured for each one and leaves the decision to you.

## What was measured

Four candidates have been evaluated so far (81 conversations, 2026-11-18, on a local Ollama); the other six have not.

| Model | Valid JSON | Agreement, clear cases | Doubtful cases | Mean per digest | RF-45 |
|---|---|---|---|---|---|
| `qwen3.5:4b` | 100% | 92.1% | 66.7% | 3.6 s | passes |
| `qwen3:8b` | 100% | 90.5% | 41.7% | 4.3 s | passes |
| `qwen2.5:3b` | 100% | 87.3% | 58.3% | 2.1 s | fails |
| `qwen3:4b` | 100% | 63.5% | 41.7% | 3.1 s | fails |

So far `qwen3.5:4b` is the best option evaluated: it passed with the highest agreement and is smaller and faster than `qwen3:8b`. This is information, not a default: nothing is configured until you run the commands below.

The numbers come from one run per model on one machine, with the evaluation set described [below](#evaluating-a-model). A model that is not in the table was not measured, which is not the same as being bad.

## Commands

### `msum ollama recommend [--all]`

Reads this machine's RAM and lists the candidates that fit, in this order: those that passed the evaluation (best agreement first), then the unevaluated ones, then those that failed.

- For each one it shows the download size, the minimum RAM and its evaluation, with the numbers.
- Candidates that need more RAM than you have are hidden (it says how many); `--all` shows them marked.
- It makes no network call, chooses nothing and writes nothing: it ends with the commands to run once you have chosen (`msum ollama pull <tag>`, then `msum provider use ollama --model <tag>`, or `provider.ollama.model` in `config.json`).

The table is in `src/infrastructure/llm/ollama-candidates.ts`: tags, parameters and sizes come from the Ollama library pages (read on 2026-11-17, listed in that file). The **minimum RAM is an estimate** (download size times 1.25 plus 3 GB), not a number Ollama publishes. The candidates are `qwen3.5:4b`, `qwen3:4b`, `qwen3:8b`, `qwen2.5:3b`, `qwen2.5:7b`, `gemma3:4b`, `gemma4:e4b`, `llama3.2:3b`, `llama3.1:8b` and `phi4-mini:3.8b`. New tags appear in the library all the time, so check it and edit the table.

### `msum ollama pull <tag> [--account <id>]`

Asks the Ollama configured in `provider.ollama.baseUrl` to download the model (its `/api/pull`), with a progress line and a check that Ollama ends with `success`.

- It sends only the tag, never chat text.
- **It only works against an Ollama on this machine** unless you add `--allow-remote` (the model is downloaded on the server that receives the request, so doing it on another computer has to be a decision).
- Server errors are shown without key-shaped text.
- Afterwards choose it with `msum provider use ollama --model <tag>` and test it with `msum provider test`.

### `msum doctor`

It also asks your Ollama for its list of models (`/api/tags`, 3 seconds, no chat text) when Ollama is the primary, the backup or serves your "local only" chats, and fails if the configured model is not installed, with the `msum ollama pull` command to fix it. `msum doctor --skip-model-check` skips that call (the check that Ollama answers is separate and stays).

## Evaluating a model

```sh
npm run eval:ollama -- --models qwen3.5:4b,gemma3:4b [--base-url URL] [--runs N] [--allow-remote]
```

### The evaluation set

It lives in `test/eval/ollama/`: **81 conversations taken from the golden files** (all made up).

- Each has the exact text the summarizer receives (`transcripts.json`, generated by `test/eval/extract-cases.mjs`) and a **hand-written label** saying whether the owner has to reply, with the reason in one line (`labels.json`; `doubtful` marks the ones a reader could argue about).
- The previous tool's answers were used only for contrast, never as truth.
- For each model and case the script calls the real `OllamaSummarizer` with the production prompt and schema and records whether the JSON was valid, whether "needs reply" matches the label (an invalid answer counts as a difference), the latency and the error.
- It prints a table and writes `test/eval/ollama/results/<date>-<model>.json` (ids and numbers, no chat text).

### How it is judged

The labeling rule is written in `test/eval/ollama/README.md` (in English).

- **Valid JSON is judged on all cases; agreement is judged only on the clear cases.** The clear cases are those not marked `doubtful` and not the six filler cases marked `jsonOnly` (which count for valid JSON and not for agreement).
- Agreement on the doubtful cases and overall are printed and saved as separate columns, for information.
- The results files committed to `test/eval/ollama/results/` are not ignored: they are what promotes a candidate to evaluated.
- **A model meets RF-45 with 100% valid JSON and at least 90% agreement on "needs reply" (clear cases).** The script exits with 1 if a model does not.
- It rejects a `--base-url` that is not on this machine unless you pass `--allow-remote`. It needs your own Ollama running with the models already downloaded; it never starts one.

### Recording an evaluation

To record an evaluation, whether it passes or not, set `evaluated: true` and `result: { date, validJsonRate, needsReplyAgreement, meanLatencyMs, passed }` in its entry of `ollama-candidates.ts` (the script prints the line) and commit it together with the results file. A test fails if a committed results file and the table do not match. Models without a results file stay "not evaluated".
